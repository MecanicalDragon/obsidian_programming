Под капотом `ReentrantLock` и большинства других [[Synchronizers|синхронизаторов]] (`Semaphore`, `CountDownLatch`, `FutureTask`) вместо `synchronized` используется другой, гораздо более гибкий механизм.

В основе всего семейства лежит класс `AbstractQueuedSynchronizer` (AQS). Вместо нативных мониторов JVM, на которых работает `synchronized`, AQS использует комбинацию трех вещей: [[CAS-FAS-FAA|CAS-операции]], `volatile`-переменной и [[LockSupport]].

`volatile int state` управляет статусом. Это обычное числовое поле внутри AQS.
- Если `state == 0`, значит, замок свободен.
- Если `state > 0`, замок занят. В `ReentrantLock` значение показывает _глубину рекурсии_ — сколько раз один и тот же поток вызвал `lock()`.

Чтобы изменить `state` без использования `synchronized`, потоки используют `CAS` операции через [[Unsafe]] или [[VarHandle]].

Если поток хочет изменить `state`, но замок уже занят, он создает объект `Node`, упаковывает туда ссылку на самого себя (`Thread.currentThread()`) и встает в высокоэффективную FIFO очередь. Оказавшись в ней, поток вызывает `LockSupport.park(this)` и засыпает.

Когда владеющий замком поток закончит работу, он вызывает `lock.unlock()` и уменьшает `state` обратно до 0. Затем он посмотрит на голову очереди ожидания и вызовет для следующего потока `LockSupport.unpark(nextThread)`. Проснувшийся поток выйдет из метода `park()`, проверит, что `state` равен 0, заберет его и продолжит выполнение.

Зачем разработчикам Java понадобилось писать эту сложную структуру на чистом Java, если уже был готовый `synchronized`? Когда `ReentrantLock` появился (в Java 5), `synchronized` был очень медленным и «топорным». Но даже сейчас, когда `synchronized` сильно оптимизировали, `ReentrantLock` на базе AQS дает огромные преимущества:
- **Возможность прерывания:** Поток, который ждет `ReentrantLock`, можно прервать из другого потока (`lockInterruptibly()`). С `synchronized` поток будет ждать намертво, его нельзя «разбудить» досрочно.
- **Ожидание по таймауту:** Можно попытаться захватить замок с ограничением по времени (`tryLock(timeout)`).
- **Честность (Fairness):** `ReentrantLock` можно сделать «честным». Тогда потоки будут гарантированно получать замок в порядке очереди. `synchronized` всегда будит случайный поток.
- **Несколько условий ожидания (Conditions):** У одного `ReentrantLock` может быть много разных очередей ожидания (аналогов `wait/notify`), что позволяет делать очень гибкие структуры данных.
